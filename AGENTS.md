# QR Code Generator

A client-side QR code generator with live preview and customization. No backend — runs entirely in the browser. Developed and maintained by [FrontSail AI](https://frontsail.ai/). Deployed at https://qr-code-gen.frontsail.app/.

## Features

- **QR types:** URL, Email, Phone, Text, vCard
- **Live preview:** Real-time QR code updates as you type
- **Customization:** Foreground/background colors (including a transparent background), gradients, 6 dot styles, corner styles, custom logo upload
- **History:** Auto-saved configurations in localStorage with restore/delete
- **Export:** Download as PNG (2x resolution) or SVG
- **Sharing:** Encode designs into self-sufficient URLs (via lz-string compression in the URL hash). Logos are excluded from shared URLs due to size constraints.

## Layout

Bun workspace monorepo:

- `apps/web` — the deployed app. React components, hooks, `index.html`, `public/`, and the Playwright suite.
- `packages/core` — `@frontsail/qr-core`: types, presets, data formatters, the qr-code-styling option mapping, and the share-link codec, plus their vitest units. Consumed as raw TypeScript source (`"exports": {".": "./src/index.ts"}`), so there is no build step.
- `packages/mcp` — `@frontsail-ai/qr-mcp`: the stdio MCP server that renders QR codes for agents. The only publishable package.
- `skills/qr-code` — the QR scannability skill, in the [agentskills.io](https://agentskills.io/specification) format: a Claude Code plugin via the root marketplace, discoverable by Codex via the `.agents/skills/qr-code` symlink, and copyable into any spec-compatible agent. Not a workspace package.
- `tools/*` — reserved in the workspace globs; empty for now.

Rules for `packages/core`: it must stay framework-free and render nothing. Its tsconfig omits the DOM lib, so `window`/`document`/`localStorage` are type errors — pass browser values in as parameters instead (see `encodeDesignToUrl`). Its only dependency is `lz-string`. React-flavored types belong in `apps/web/src/types.ts`. A formatter returns `""` for a form with nothing in it, and that empty string is the only signal of "nothing to encode" the whole system has — the web app's empty state and export lock, the render hook's early return, and the MCP server's `InputError` all derive from it. Anything arriving from outside React state — a share link, the persisted draft, a history entry — is validated by `normalizeDesign` before it is rendered, for the same reason: one notion of what a valid design is, not one per entry point, and it is what stops a value stored by an older build (or hand-edited into a link) from reaching the renderer. The check lives once in `formatQRData`, not per formatter: five private notions of "empty" is how a blank vCard came to encode a hollow `BEGIN`/`END` card (#36). Normalize whitespace wherever it is syntactically invalid (a `mailto:` addr-spec, a vCard value); leave it alone only where the field _is_ the payload (`text`). User text entering a structured payload goes through that format's escaping rules, verified with hostile-input tests — raw interpolation is how the mailto form-encoding and vCard semicolon bugs shipped. All five formatters now hold this line, and the rule is a sweep rather than a per-format patch: percent-encoding per RFC 6068 for `mailto:` (recipient included, not just the query), backslash escapes and CRLF per RFC 2426 for vCard, percent-encoding of the characters STD 66 excludes for `url`, and the RFC 3966 subscriber grammar for `tel:`. When a value cannot be represented in its format, encode nothing rather than dropping the offending characters — deleting the letters from a phone number's `ext. 89` leaves `.89`, whose `.` is a valid visual separator, so the result is a well-formed URI that dials somewhere else. `formatQRData` returning `""` therefore now means "empty _or_ unrepresentable"; callers that report the difference to a human ask `hasAnyContent` which of the two it was (see `packages/mcp/src/server.ts`).

Rules for `apps/web`:

- **The build prerenders, and the crawler suite is the proof.** `vpr build` runs three stages: the client build, an `--ssr` build of `src/entry-server.tsx`, and `scripts/prerender.mjs`, which renders the app under a jsdom shim and injects the markup into `dist/index.html`'s `#root` — so crawlers that do not execute JavaScript still read the page (#78). The script fails the build rather than ship an empty shell, and the `crawler` Playwright project (JS disabled, against the built output) pins the words in CI. Anything that must be crawler-visible has to exist at first render without effects; content that appears only after an effect runs is invisible to every non-JS crawler.
- **User-facing failures are inline, never native dialogs.** `alert`/`confirm`/`prompt` are lint errors (`no-alert`, configured in the root `vite.config.js`). Render the `Note` primitive from `src/components/ui.tsx` instead — `variant="error"` with `role="alert"` for something the user just did.
- **An input with more than one entry point has one intake, not one per entry.** The logo can arrive from the picker in the inspector or from a drop anywhere on the canvas; both go through `useLogoIntake`, which owns validation _and_ the rejection message. Sharing only the validator is what let the two paths drift into an `alert()` and a silent `return` for the same file (#37).
- **The user's working state has an owner, and a failed persist is reported rather than logged.** The design being edited lives in `useDraft`, which writes it through `src/utils/safeStorage.ts` — the only module allowed to touch Web Storage, enforced by `no-restricted-globals` in the root `vite.config.js`. Durability used to be a side effect of downloading, so a refresh threw away anything not yet exported (#42); worse, the one path that did persist caught its own `QuotaExceededError` and logged it while the toast and the sidebar both reported a save that never happened. `writeItem` returns a `WriteResult` instead of throwing so that "it did not get stored" cannot be dropped by accident, and every caller renders the failure where the user just acted. The draft is keyed per tab (a `sessionStorage` id), which is what keeps two open tabs from overwriting each other's work without needing a lease.
- **What the app remembers about storage is a cache, not a fact — and something has to ask.** `useDraft` keeps the fingerprint of the design it last wrote so it can skip re-serialising a 2.8 M-character draft that has not changed. That record answers "has the design changed?" when the question is "is what I wrote still there?", and `localStorage` is not this tab's to assume about: another tab's sweep takes slots, the browser evicts under pressure, the user clears site data with the tab open. Believing it meant the draft was never written again for the rest of the session, silently, with the work still on screen looking saved (#65). Two halves, and both are load-bearing — each is proven by its own pair of tests. The skip is predicated on the slot still being there, _and_ the write gets occasions to run that are not "the design changed": a `storage` event naming the slot, the tab becoming visible again, and the flush on the way out. A guard that is never reached guards nothing. The same rule is why history reads its unreadable entries back from storage at write time rather than remembering them from boot — remembering them wrote deleted entries back.

- **A message rendered off-screen is a silent failure, and geometry cannot tell you it is on screen.** `toBeVisible()` passes on a node scrolled out of the viewport; `toBeInViewport()` passes on a single visible pixel; and `toBeInViewport({ ratio: 1 })` — the tightening that caught the last one — passes on an element lying _underneath_ a fixed overlay, because it compares rectangles and knows nothing about what is painted on top. That is how the storage warning came to be scrolled squarely behind the consent banner with its own test green. Use `expectUnobstructed` from `apps/web/tests/support/reachability.js` for anything the user has to see or click: it asserts the geometry **and** hit-tests the element's top and bottom, and names whatever is covering it when it fails. The bare `toBeInViewport()` passes on a **single visible pixel** — which is how a note sitting 50px below the fold was recorded as being in the viewport for two releases (#61). Every use in the suite omitted the ratio; tightening them turned up a rejection message spilling 0.39px past the panel edge as well.
- **The same rule covers controls, and covers what the message says.** Off-screen is one way for the UI to fail to reach someone; there are three more, and each has cost us a bug. A control can be _underneath_ another one — the mobile export bar sat below the consent banner, so a tap aimed at Download landed on "Accept" until the bar took the `--consent-inset` every other fixed element already took. It can be _past the edge_ — vCard sat 29px beyond a 390px viewport in a scrolling row with no fade, no partial chip and no scrollbar, which is a type most people never find. It can be _under the contrast floor_ — `--text-muted` was `--ink-400`, 2.99:1 on paper, for text as load-bearing as the character counter. And it can be _saying the wrong thing_: `formatQRData` returns `""` for both "empty" and "cannot be represented", and the app told someone staring at a filled-in phone field to "add some content" — `hasAnyContent` is what separates the two, and the MCP server had been asking it since #54. Assert reachability the way you assert visibility: `toBeInViewport`, a hit test at the control's own centre (`elementFromPoint`), a measured contrast ratio.
- **The canvas column has a tail, and the tail is where the warnings live.** It is anchored to the top and grows downward (#66), so on a window shorter than the column its end runs past the fold — and its end is the advisories and the export controls. At 1280x640, an ordinary 1366x768 laptop once chrome is taken off, the storage note sat at y643 with the page ending at 693; with a colour advisory stacked above it, Download itself was left with 4px on screen. Anything appended there brings itself into view when it appears: `scrollIntoView({ block: "nearest" })` moves the least it can and does nothing on a window tall enough, plus a little `scroll-mb-*` so it does not land flush against the edge, plus room under the column for it to scroll into. Scrolling the document is safe here precisely because the inspector is sticky — the field being typed into does not move.
- **`--consent-inset` is the app's only statement of where the banner is.** It is the banner's measured height (a `ResizeObserver` in `ConsentBanner`), zero once answered, and everything that must stay clear of the bottom of the window consults it: both asides subtract it from their height, the toast and the mobile export bar add it to their offset, the canvas pads by it. There is no notion of a "safe" viewport anywhere — each element remembers separately, so anything new that positions against the bottom edge has nothing to inherit and must include it explicitly. That includes scroll margins: `scrollIntoView` aligns to the viewport, which does not know its lower reaches are spoken for, so a flat `scroll-mb-*` on the storage notice parked it exactly where it could not be read.
- **A confirmation that sits where the trigger sat is not a confirmation.** "Clear all" arms in place, so the second click of a double-click landed on "Confirm?" and took three saved designs to zero. Inline arming is still the right shape — a modal for one button is heavier than what it guards — but it has to ignore clicks for longer than the platform double-click threshold, so the question can only be answered by a click aimed at the question. Test the gesture, not just the click: a single click proves the guard exists, a double-click proves it guards.
- **A control that destroys user data offers a take-back, and the take-back is not a message.** The handler snapshots what it is about to overwrite and pushes it to `useUndo`; `useToast` carries transient messages and is deliberately incapable of holding an action. This is a capability rule, not a per-button one: while the toast was text-only, every irreversible path could only choose between saying nothing and a native dialog `no-alert` forbids, so all five of them — delete, clear all, restore, a share link landing in a loaded tab, removing the logo — said nothing, and a mis-clicked hover icon was final (#41). Undo restores _position_, not just presence: reinserting a deleted entry at the top hands back a history the user never had. Confirmation is the exception, reserved for blast radius rather than for gesture — "Clear all" arms inline before firing because it is the one control that can cost months of designs at once, and it still offers the undo afterwards.
- **Keep undo's lifetime out of the notification's.** The first version of the rule above ended "…and the toast's action slot is where it lives", which is how the action came to be a _field of_ the toast — and that quietly made undo capacity a property of display capacity. A strip shows one message, so the app held one take-back, and every message evicted it, including the three that announce nothing destructive: deleting a design and then downloading a PNG lost the design (#57). `Toast` may draw a message _over_ a pending offer, but only `useUndo` decides when an offer ends. Consecutive same-kind actions coalesce into one offer and replay newest-first, because `insertConfig` restores by position and an oldest-first replay reinserts against a list that has already shifted.
- **The undo store is a stack, and no destructive action may cost another one its take-back.** Coalescing alone widened the slot without deepening the store: a different _kind_ still replaced whatever was held, so deleting a design and then removing a logo cost the design, and one stray delete could drop a "Cleared 47 saved designs" (#57 again — the half #58 knowingly left). Same-kind actions still merge into the top group; an unrelated one lands _on top_, and taking the top re-offers what was underneath. Merging across kinds instead is one line and wrong — a single "Undo" reversing two unrelated things under a label naming only one of them is a worse surprise than the bug. The window covers the whole stack and restarts on every change, including a pop, so undoing at the 5.9-second mark does not leave a tenth of a second to notice the next offer; depth is capped (`MAX_DEPTH`) because the window is rolling and a design snapshot can carry a multi-megabyte logo.
- **A message and a take-back are two shapes, and depth is shown rather than re-offered.** `Tray` draws both at the bottom centre: a message is an ink line with an icon and no controls, a take-back adds a rule across the top that drains as the window runs out, a mono `Reversible — n`, and a _list_ of the pending groups. The list is what fixes the misreading — a label that changes in place half a second after a click reads as "that did not work", so undoing subtracts a row from something visible instead. It also makes depth reachable: `takeThrough(n)` reverses n groups newest-first, and hovering a depth control tints exactly the rows it would take. A coalesced group discloses its payloads read-only and is never divisible — entries restore by the index they held, so reversing #2 without #3 reinserts against a list that has already shifted. Pointer or focus anywhere over the tray holds every clock and leaving resumes with a floor, because a list you are meant to read must not expire while being read. `⌘Z`/`Esc` are bound only while a window is open and never when the event target is a field — inside one, `⌘Z` already means "undo my typing". Idle mounts nothing: no parked node, no `opacity: 0` control in the tab order. The drain is exempt from the blanket `prefers-reduced-motion` rule in `plico.css` and steps instead, because collapsing it to `0.01ms` would delete the information rather than the movement.

Rules for `skills/`:

- **The plugin root is `skills/qr-code/`, not the repo root.** `.claude-plugin/marketplace.json` at the repo root points `source` at `./skills/qr-code`, which holds its own `.claude-plugin/plugin.json` and `SKILL.md` (the documented single-skill-at-plugin-root form). Pointing `source` at `"./"` also works and installs the whole monorepo — 345 MB, because the root `package.json` makes the installer run a dependency install. Keep the plugin root free of `package.json`.
- **Every scannability claim in `SKILL.md` is cited or measured.** The measurements come from `packages/mcp/tests/scannability.test.ts`; the evidence table is in `docs/plans/2026-08-01-qr-skill.md`. Do not add a claim to the skill without adding its evidence, and if a threshold in that test moves, update the skill — and revisit `packages/core/src/scanRisk.ts`, whose warning thresholds anchor the web app's colour-scannability warning to the same measurements.
- **The skill must agree with the MCP tool descriptions.** They ship to the same audience; a contradiction between them is worse than either being silent.
- **The skill is versioned, and the version lives in two files that must agree:** `SKILL.md` `metadata.version` and `.claude-plugin/plugin.json` `version`. `packages/mcp/tests/skill.test.ts` enforces the sync, along with the agentskills.io frontmatter constraints and the plugin↔marketplace description duplicate. Any behaviour-visible change to `packages/mcp` — tool parameters, defaults, error-correction level, quiet zone, logo footprint — requires reviewing `SKILL.md` and bumping the skill version in both files.
- **The skill body is agent-neutral; agent-specific install steps live in `README.md`.** The skill ships to Claude Code, Codex, and anything else that reads the spec, so `SKILL.md` may name agents only where their commands genuinely differ (the MCP-registration block in §4), never assume one host.
- Run `claude plugin validate . --strict` (`just validate-plugin`) after touching either manifest — CI runs it too, but a red push costs a round-trip.

Rules for `packages/mcp` — each of these was learned by watching a plausible-looking but wrong file get produced, so treat them as invariants rather than preferences. Plausible output, not loud failure, is this project's characteristic bug: the defences that have actually caught things here are pixel-level assertions on decoded output, reading `npm publish --dry-run` warnings instead of skimming past them, and pointing a real agent at the result rather than trusting integration tests.

- **Core is bundled, not depended on.** `@frontsail/qr-core` sits in `devDependencies` precisely so `vp pack` inlines it (with `lz-string`) into `dist/index.mjs`. Moving it to `dependencies` would publish an import of a private package that no consumer can resolve. Core's raw TypeScript is not loadable by plain Node either way.
- **The library's own canvas/PNG path is forbidden.** Never `type: "canvas"` + `getRawData("png")`: it silently drops logos with node-canvas 2 and paints solid squares with the napi canvas. PNG is always resvg rasterizing the sanitized SVG.
- **Never add the `canvas` (node-canvas) package.** It carries a `prebuild-install || node-gyp` postinstall that npm is moving to block, and it segfaults under Bun. `@napi-rs/canvas` is the supported canvas.
- **`nodeCanvas` is always passed, and every `getRawData` call keeps its timeout.** Without a canvas implementation the logo path returns a promise that never settles — a tool call that hangs forever, which is worse for an agent than any error. The same never-settles hazard exists in the browser (the library's image loader has no `onerror`, so an undecodable logo stalls drawing silently); the web app guards it with byte-level upload validation (`apps/web/src/utils/validateLogoImage.ts`) plus the render watchdog in `useQRCode` — keep both when touching the logo path.
- **Sanitize on the PNG path only.** The `url('#id')` → `url(#id)` rewrite is what makes resvg work, but it changes bytes; applying it to returned SVG would break byte-parity with the web app, which `tests/parity.test.ts` guards using SVGs captured from the live site.
- Test fixtures must be real-world PNGs. resvg decodes node-canvas-2-encoded PNGs as black, so a fixture built that way would fail for reasons unrelated to the code.
- **A Dependabot bump that reddens the golden or parity tests is the system working, not flakiness.** `qr-code-styling`, `@resvg/resvg-js` and `@napi-rs/canvas` all decide what gets rendered, so a failure there means that bump changed the output. Read the pixels and decide whether the new rendering is acceptable _before_ touching a golden. Regenerating first converts a detection into a silent acceptance, which is precisely the failure mode every other rule in this section exists to prevent.

## Submitting changes

Before reporting work as complete to the user, always run:

```bash
just lint
just test
```

When the user asks to push changes to GitHub, always:

1. Run `just lint` and `just test` — fix any failures before proceeding.
2. Submit changes in a new pull request (not directly to master).
