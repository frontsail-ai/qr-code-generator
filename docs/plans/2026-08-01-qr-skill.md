# QR scannability skill blueprint

**Date:** 2026-08-01 · **Status:** proposed · **Scope:** one PR, new `skills/` tree, no behavior change to any package

Add `skills/qr-code/` — the judgment layer the MCP server deliberately lacks. The tools answer "render this design"; the skill answers "is this design a good idea", and teaches an agent to fix it when it isn't.

## Why

[PR #14](https://github.com/frontsail-ai/qr-code-generator/pull/14) gave agents the ability to generate any design the web app can. It gave them no way to know which of those designs will fail to scan. An agent asked for "a QR in our brand colours, transparent, with the logo" will produce exactly that — and the result may be unscannable for reasons that are invisible in the returned SVG: no quiet zone, a foreground too light, a transparent background about to land on a dark slide.

The tool descriptions are the wrong place for this. They document parameters; scannability is a judgement about the combination, and it needs room to explain trade-offs.

## Target layout

The repo becomes its own single-plugin marketplace. Skills are not workspace packages — no `package.json`, nothing in the workspace globs, per the [monorepo blueprint](2026-07-31-monorepo-restructure.md).

```
.claude-plugin/
  marketplace.json   ← catalog; source points at ./skills/qr-code
skills/
  qr-code/           ← the plugin root
    .claude-plugin/
      plugin.json    ← plugin manifest (name, description, version)
    SKILL.md         ← the skill itself
```

The plugin root is `skills/qr-code/`, not the repo root. That is deliberate and load-bearing — see the Outcome; pointing the marketplace at `"./"` installs the entire monorepo.

## Design decisions

- **Every claim carries an evidence tag.** This project's characteristic failure is plausible-looking wrongness, and a skill full of confident folklore is that failure in prose. Each scannability claim is either **cited** to the standard or **measured** by a committed harness. Nothing is asserted from intuition.
- **The harness is a committed test, not a throwaway script.** It lives at `packages/mcp/tests/scannability.test.ts` — the one place the brief allows package changes — so the numbers stay re-checkable. If a dependency shifts a threshold, the test moves and the skill has to move with it.
- **jsQR is a proxy, and the skill says so.** The harness decodes clean rasterized bitmaps with no optics, motion blur, glare, perspective or print gain. Every threshold is therefore a _generous upper bound_. Findings are phrased "fails below X"; a decode at X proves nothing about a phone at X.
- **The skill is instructions, not documentation.** Rules and thresholds inline; the measured tables stay in this blueprint and are linked. A skill body is loaded into context when it fires, so length has a real cost.
- **The skill must not contradict the shipped tool descriptions.** `corner_square_type: "extra-rounded"` is what the UI labels "Rounded" (still true), and gradient direction names are correct as of [#16](https://github.com/frontsail-ai/qr-code-generator/pull/16) — the earlier "names are rotated" warning is gone and must not be reintroduced.

## The app's real QR parameters

Read from code and measured, not assumed:

| Parameter        | Value                                | How established                                                               |
| ---------------- | ------------------------------------ | ----------------------------------------------------------------------------- |
| Error correction | **Q** (~25% recoverable)             | qr-code-styling default; core sets no `qrOptions`. Verified by byte-identity  |
| Quiet zone       | **none** (0–6 modules of slack)      | `margin` defaults to 0; core sets none. Measured                              |
| Logo size        | 61px on a 280px canvas = 5.5 modules | Measured from the emitted `<image>` element                                   |
| Logo clear area  | +8px margin each side ≈ 7 modules    | `imageOptions.margin: 8` in `qrConfig.ts`; `hideBackgroundDots` defaults true |
| Logo coverage    | ~10% of dark modules                 | Measured at two content lengths                                               |
| SVG export       | 280px                                | `SVG_SIZE` in the MCP package; matches the web preview                        |
| PNG export       | 560px                                | `PNG_SIZE`; matches the web app's 2× download                                 |

The quiet-zone result is the headline. The web UI's card padding supplies a quiet zone _visually_, so the design looks safe on screen — but the exported file has none. A bare export dropped onto a busy background loses the quiet zone entirely, and the user has no way to notice from the app.

## What the measurements contradict

The findings that justify the skill's existence, because each one reverses common advice:

1. **"Keep contrast above 3:1 and you're fine."** Two sweeps through the same ratios give opposite answers. Lightening the foreground fails at 3.95:1; darkening the background still works at 1.68:1. A binarizer thresholds luminance to decide which modules are dark — so the rule is _keep the dark modules genuinely dark_, not _keep the two colours far apart_. A pale-grey-on-white code passes WCAG for graphics and does not scan.
2. **"Fancy dot styles hurt scannability."** All six styles decode within one ladder step of each other (1.6–2.0 px/module). At the sizes where codes actually fail, physical size dominates and style is noise. Style is a design choice, not a scannability one.
3. **"Long content plus a logo is the risky combination."** The logo scales with the canvas, not the module count, so it hides a near-constant ~10% of dark modules whether the payload is 20 characters or 306. Length and logo are close to independent risks.
4. **"The app's exports include a quiet zone."** They do not, and the UI actively hides this: the card padding around the preview supplies the margin on screen that the file lacks.

## Plan

1. **`packages/mcp/tests/scannability.test.ts`** — the harness. Contrast sweeps in both directions, transparent-on-surface matrix, logo coverage at two content lengths, dot-style size ladder, quiet-zone measurement. Adds `jsqr` as a devDependency; no `src/` changes.
2. **`.claude-plugin/plugin.json`** — plugin manifest, name `qr-code-generator`, so the skill resolves as `/qr-code-generator:qr-code`.
3. **`.claude-plugin/marketplace.json`** — one-plugin catalog, `source: "./"`, marketplace name `frontsail-ai`.
4. **`skills/qr-code/SKILL.md`** — frontmatter `description` tuned for triggering (QR codes, scannability, styling, logos, share links). Body ordered: pick the content type → style within safety rails → the traps → generate via the MCP tools when present, else emit a share link.
5. **Validate and install for real** — `claude plugin validate`, then `/plugin marketplace add`, `/plugin install`, and confirm the skill loads and fires in a fresh session. Assumption 3 stands or falls here.
6. **Docs** — `AGENTS.md` gains a `skills/` section; `README.md` gains one line plus the install command.

## Project conventions honored

- **[`AGENTS.md`, "Submitting changes"]** `just lint` + `just test` before reporting complete → both run; the harness joins the existing suite.
- **[monorepo blueprint]** `skills/` holds SKILL.md folders and is deliberately not a workspace package → no `package.json`, no workspace glob entry.
- **[PR #15 tool descriptions]** The skill must agree with them → corner naming repeated as shipped; gradient directions described as they render post-#16.
- **[this repo's blueprint pattern]** Plan first, implement in the same PR, record deviations in an Outcome section.

## Risks & mitigations

- **jsQR flatters every design.** A synthetic decoder on a clean bitmap tolerates far more than a phone. Mitigation: thresholds framed as upper bounds, the proxy limitation stated in the skill itself, and the inverted-code caveat cited rather than measured.
- **Assumption 3 (both manifests in one `.claude-plugin/`) may not be supported.** Mitigation: gated on a real install before merge. Fallback is moving the plugin into a subdirectory and pointing `source` at it, which costs one path change.
- **Thresholds drift with dependency versions.** Mitigation: they are assertions in a test that runs in CI, not prose in a document.
- **Skill bloat.** A long body costs context every time it fires. Mitigation: rules inline, evidence linked here.

## Out of scope

Publishing the plugin to the community marketplace. A scannability _tool_ in the MCP server (this is instructions, not code). Print-specific guidance (DPI, substrate, ink gain) — unmeasurable here and better cited than guessed. Correcting the quiet-zone gap in the app itself: that is a real product change, and it belongs in its own PR with its own visual review.

## Success criteria → plan mapping

- Agent gets judgement, not just parameters → skill body ordered by decision, not by API surface (step 4)
- No folklore → every claim tagged in the evidence table; the four contradictions above are the value
- Claims stay honest over time → harness committed and running in CI (step 1)
- Actually installable → executed install, not a documented one (step 5)

## Outcome (2026-08-01, post-implementation)

Deviations from the plan as written:

1. **Assumption 3 refuted; the layout changed.** Making the repo root the plugin (`source: "./"`) validates cleanly and the skill loads — but installing it materialises **345 MB**, because the plugin root has a `package.json` and the installer runs a dependency install. Proven by isolating the variable: an otherwise identical source directory with no `package.json` installs at 16 KB. Final layout puts the plugin root at `skills/qr-code/` using the documented single-skill-at-plugin-root form, with `.claude-plugin/marketplace.json` at the repo root pointing `source` at `./skills/qr-code`. The skill file stays exactly where the brief specified. **Install is now 12 KB, ~99 tokens always-on.**
2. **An intermediate layout was tested and rejected on a confounded reading.** Placing `plugin.json` in `skills/.claude-plugin/` appeared to work — the skill showed up in a fresh session — but `claude plugin details` reported `Skills (0)`. The skill being listed came from a _different_ install still present under the same plugin name. Cleaning every test marketplace and re-testing from a known-empty baseline is what surfaced it. Worth remembering: two plugins may share a plugin name across marketplaces, so a skill appearing proves nothing about which one provided it.
3. **Marketplace renamed `frontsail-ai` → `frontsail-qr`.** The machine already had a marketplace named `frontsail` sourced from `frontsail-ai/fs-skills`; two near-identical names would be a trap. See open question 1 — that repo may be the more natural long-term home.
4. **The skill gained a "What you can and cannot change" section** after dogfooding. Asked for a banner QR, an agent confidently promised to "bump the error correction level to H to pay for the logo" — impossible here, since this toolchain is fixed at Q with no parameter. The skill had been silent on what is _not_ adjustable, so the model filled the gap from priors.
5. **Skill invocation is not guaranteed, and that is a property of the system, not a defect here.** When the skill fires it is authoritative: asked directly about this toolchain's quiet zone and EC level, a fresh session returned the measured numbers verbatim (0.18 modules, level Q, fixed). But a prompt that embeds a confident false premise ("bump EC to H") and asks for a short answer can be answered from priors without the skill loading — this reproduced even after widening the description with `error-correction`, `quiet zone` and `print` trigger terms. Explicit invocation (`/qr-code-generator:qr-code …`) always loads it and always gives the grounded answer. Users who need the guarantee should invoke explicitly.

## Open questions

1. Marketplace name `frontsail-qr` — user-facing in `/plugin install qr-code-generator@frontsail-qr`. Note this machine already carries a `frontsail` marketplace pointing at `frontsail-ai/fs-skills`; if that repo is the intended home for FrontSail skills, this skill arguably belongs there instead and this marketplace should not exist. Flagged rather than decided, since the brief placed the skill in this repo.
2. Whether the quiet-zone gap should also be fixed in the app (adding a `margin` to the export). The skill can only tell agents to compensate; the app could stop creating the problem. Flagged for a follow-up, deliberately not bundled here.
3. Whether to set `disable-model-invocation` — currently left off so Claude can apply the skill automatically when a QR task appears, which is the point. Revisit if it fires too eagerly.
